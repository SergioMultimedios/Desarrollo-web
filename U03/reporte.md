En esta unidad se le agregó al proyecto el dominio académico. Hasta ahora solo había un controlador que devolvía un saludo, sin tipos propios. Se partió de la carpeta U03/inicio, que es la solución de U02. Fueron cinco cambios. Al pom.xml se le subió la versión a 0.0.3-SNAPSHOT y se le cambió el nombre y la descripción a la unidad 03, sin agregar dependencias. Se creó el record Alumno, el enum EstatusAlumno y el record Materia, los tres en el paquete mx.edu.backendacademico.domain. Y se creó la prueba AlumnoTest en el mismo paquete pero del lado de test.

Alumno es un record con id, matricula, nombre, correo y estatus. Lo que hace el trabajo es el constructor compacto. Ahí se rechaza un id menor o igual a cero, se pasa la matrícula a mayúsculas con Locale.ROOT y se revisa que nombre y correo no vengan vacíos ni se pasen de largo. El método darDeBaja() no cambia el objeto. Devuelve un Alumno nuevo con el estatus en BAJA, así que el original se queda como estaba. EstatusAlumno es un enum con ACTIVO y BAJA nada más, para no andar usando cadenas libres. Materia lleva clave, nombre y créditos, y su constructor no deja pasar texto vacío ni créditos en cero o negativos.

Se corrió .\mvnw.cmd -Dtest=AlumnoTest test, que es la prueba del dominio sola, y dio Tests run: 3, Failures: 0, Errors: 0 con BUILD SUCCESS. Después se corrió .\mvnw.cmd test completo y dio Tests run: 4, porque suma las 3 del dominio más la del contexto que venía de antes. En la salida ya se ve que compila 5 fuentes en lugar de 2. Estas pruebas no levantan servidor ni base de datos, construyen los objetos directo desde Java.

También se verificó que el saludo siguiera funcionando. Se levantó el servidor con .\mvnw.cmd spring-boot:run y el GET a /api/v1/saludo dio 200 con {"mensaje":"Hola backend"}, igual que en la unidad pasada. Agregar el dominio no le movió nada al controlador.

Para el reto se le agregó el método reactivar() a Alumno, que es el espejo de darDeBaja(): devuelve un Alumno nuevo con el estatus en ACTIVO. Se escribieron dos pruebas más, así que AlumnoTest quedó en 5 y el total en 6. La primera parte de un alumno en BAJA, le llama reactivar() y comprueba que el nuevo quede en ACTIVO mientras el original sigue en BAJA, con el mismo id y la misma matrícula. La segunda arma dos alumnos con el mismo id y la misma matrícula pero distinto correo, y comprueba con assertNotEquals que no son iguales.

Esa segunda prueba es la que deja ver la diferencia entre dos cosas que se confunden. El equals de un record lo genera Java comparando todos los componentes, así que cambiar una sola letra del correo ya hace que los dos valores no sean iguales. La identidad académica es otra cosa y va por el id y la matrícula, que es lo que de verdad dice si se trata del mismo alumno. O sea que esos dos objetos no son iguales como valores, pero sí son el mismo alumno con el correo actualizado. Por eso más adelante la unicidad se va a cuidar con la matrícula en la base de datos y no con el equals del record.
